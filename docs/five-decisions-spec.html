Spec: Five pstack Mechanisms as Jev Decisions

2026-09-21 · @Someone

Purpose

Build five mechanisms from Cursor's pstack plugin into Titanium Bot as Jev decisions in JDE, not as prompt text. pstack is ~81k words of markdown that assumes a frontier model re-reads it every turn; Titanium Bot's workspaces run Nemotron 30B, GLM-5.3 Flash, Qwen 3.8 Max and MiniMax M3 on a 75M-token 5-day allowance, and 20 of pstack's 23 playbooks are about shipping code while customers run marketers and research bots. The thesis transfers; the artifact does not.

The thesis is the same one JDE already runs on: facts stay in code, the model gets only the semantic step. pstack's version is "never hand the human a check you could run." JDE's version is a ledger, calibrated probabilities and blind sets. This spec ports the five pstack ideas that survive that translation.

What this spec asks Claude Code to build, in order:

  • task-restatement — a decision (score / per-part yes-no)
  • ask-gate — a decision (choice)
  • claim-labeling — a decision (choice + yes-no)
  • Room hygiene — a rooms policy, with one optional decision (promotable, yes-no)
  • playbook-route — a decision (choice) plus a playbook-as-data format and a disposition check in code

Sources this spec draws on: JDE, the pstack source (v0.15.2), the pstack marketplace page, and Lauren Tan's pstack guides Part 1 and Part 2.

Ground rules every decision inherits

Every decision below is a new policy.json entry, a cases/<decision>-blind.json set, and an ask() call site, following the same rules completion-check already obeys. Nothing here relaxes them.

  • Typed questions only. Choice, yes-or-no, or score. Never a prose answer to parse. Jev's choice cardinality tops out at 255, so any catalog larger than that goes two-stage (score independently, then choose).
  • One question per part. The whole-task question scored in the seventies; per-part questions plus code aggregation scored 100%. Decompose before asking.
  • Facts stay in code. Whether a receipt is attached, whether a tool exists in the bot's manifest, whether every step has a disposition: if statements, never questions.
  • Aggregation belongs to code. The judge never sees how its answers combine.
  • A band for every case, including the bottom. Every decision names its accept, revise/hold, and escalate bands and what code does in each.
  • Timeout and fallback are required. A judge that does not answer must never change what the bot would otherwise have done. Every fallback below is fail-open to current behaviour, plus a ledger flag.
  • One call, no retry. Same as today.
  • Ledger every judgment. Decision, state hash, answers, confidences, band hit, action taken, agentId, turnId, workspaceId, roomId where applicable.
  • Blind set before ship. Written by someone who did not write the questions and never saw a result. Floor is 30 cases per decision; the case author signs off before the first eval run, and there is no tuning after.
  • Offline first. Every decision must pass its policy, band and fallback tests against the code judge with no key and no network before it is pointed at Jev.
  • Budget. Target the completion-check envelope: p50 under ~200 ms, well under a cent per call. A decision that needs more than one Jev round-trip per bot turn needs a stated reason.

Build order

Restatement first, router last. Each step reuses the shape of the one before it, and the router is the only one that cannot be built until a playbook catalog exists as data.

OrderItemKindWhy here
1task-restatementdecisionCheapest; closest to what completion-check already measures; every later decision is better when the task was read correctly
2ask-gatedecisionSame choice-over-context shape as restatement; the one customers will feel first

Decision 1 — task-restatement

Before a bot does any work, it restates the task in its own words and Jev scores whether that restatement matches the request. This is pstack's "indirect prompt" (restate the problem before acting) turned into a gate; it catches a misread before tokens are spent going the wrong direction, where completion-check catches it only after.

Fires: once per task, after the bot's first turn produces a restatement block and before the first tool call. Applies to lead agents and to any bot that receives a task from a room or a schedule.

State: { task, taskParts, restatement, workspaceId }. taskParts comes from the same parts extraction completion-check uses; do not build a second one.

Questions (all per part, code aggregates):

  • yes-or-no, one per taskPart: Does the restatement cover this part with the same meaning?
  • yes-or-no, once: Does the restatement add a requirement the request did not contain?
  • yes-or-no, once: Is the restatement a near-verbatim copy of the request? (Parroting shows no reading. Code can pre-screen this with a similarity ratio; the question is for paraphrase-parrots the ratio misses.)

Code, not questions: part count, the similarity pre-screen, and the aggregate.

Bands:

BandConditionAction
acceptevery part covered at or above threshold, no added requirement, not a parrotproceed
reviseone or more parts below threshold, or an added requirementreturn the uncovered part ids to the bot with a one-line reason; bot restates once more; at most 2 revise loops, then escalate
escalateparrot, or still failing after 2 loops, or any confidence in the bottom bandroute to the workspace's approval path with the request and both restatements side by side

Fallback on timeout: proceed (today's behaviour) with restatement: unjudged in the ledger. Never block a customer's job on a judge timeout.

Ledger fields: per-part answers and confidences, added-requirement answer, parrot answer, similarity ratio, band, loop count.

Blind set (30 minimum, author never saw the questions):

  • correct restatements across marketer, research and engineering tasks
  • a dropped part (3-part task restated as 2)
  • an added part (bot volunteers a deliverable nobody asked for)
  • a misread constraint (wrong platform, wrong audience, wrong date range)
  • right words, wrong meaning (same nouns, inverted intent)
  • verbatim and near-verbatim parrots
  • a restatement that reorders parts but covers all of them (must pass)

Done when: blind set passes, offline tests cover all three bands and the timeout path, the console shows the restatement and its band on the task, and the ledger row appears in api.titanium.bot/admin.

Decision 2 — ask-gate

Before a bot sends a question to a human, Jev classifies it: answerable by a tool the bot has, a genuine preference call, or blocked on something the bot lacks. Only the last two reach the human. This is pstack's AskQuestion rule ("if it's runnable, it's not the human's to answer") as a typed choice instead of a paragraph of instructions.

Fires: on every outbound message the bot marks as a question to a person, in rooms and in direct tasks. Sits in the send path, not in the bot's prompt.

State: { question, taskSummary, toolManifest, recentToolCalls, workspaceId }. toolManifest is the bot's enabled skills as name plus one-line description, straight from the skills panel; do not hand the judge full tool schemas.

Questions:

  • choice, once: { runnable, preference, blocked } — Which best describes how this question gets answered?
  • choice, only when runnable: pick the tool from toolManifest (cardinality is the manifest length, so it stays under 255)
  • yes-or-no, only when runnable: Did the bot already try this tool for this question? (a retry loop is not a reason to suppress again)

Code, not questions: whether the manifest is empty, whether the chosen tool exists, the already-tried count from recentToolCalls, and the no-second-suppression rule.

Bands:

BandConditionAction
suppressrunnable at or above threshold, a tool was chosen, not already trieddo not send; return the question to the bot with run: <tool> and a one-line reason
passpreference or blocked at or above thresholdsend to the human unchanged; blocked carries the reason so the human knows what to unblock
pass-flaggedany confidence in the bottom band, or runnable but already triedsend to the human; ledger flags it

There is no band that swallows a question silently. The failure mode this must never have is a customer waiting on a bot that decided not to ask.

Fallback on timeout: pass (today's behaviour), ledger ask-gate: unjudged.

Ledger fields: the question text, verdict and confidence, chosen tool, whether the bot then ran it, and whether the run produced an answer. The last two fields are the metric: suppressed questions that the bot could not actually answer are the false positives to watch.

Blind set (30 minimum):

  • runnable: "how many posts went out last week", "is the client's site up", "what version is deployed", "does the doc mention pricing"
  • preference: tone, which of two drafts, budget ceiling, whether to reply to a hostile comment
  • blocked: needs an API key, a login, a permission the workspace has not granted
  • traps: reads as preference but a tool answers it ("which logo do we use" when the brand file is in Drive); reads as runnable but needs private knowledge ("what did the client say on the call" when there is no transcript tool)
  • a question the bot already tried to answer with a tool and failed (must pass, not suppress)

Metric to publish: questions-to-human per completed task, before and after, per workspace. That number is the pitch for this decision.

Done when: blind set passes, offline tests cover all three bands and the timeout path, the false-positive rate from the ledger is visible in admin, and a suppressed question is visible to the workspace owner in the bot's trace (not hidden).

Decision 3 — claim-labeling

Research bots tag every claim they emit as measured, inferred or guess, and Jev checks that the label matches the evidence attached. A guess that a tool could turn into a measurement is sent back. This is the agent-side half of completion-check: the bot admits its confidence while writing, instead of the judge reconstructing it afterwards.

Agent-side contract (prompt/format change, not a decision): research output is a list of claims, each { text, label, receipts[] }. A measured claim must carry at least one receipt in the same receipt format completion-check already consumes (URL read, tool result id, file pointer). This is the only prompt-level change in this spec, and it is a format rule, not guidance.

Fires: when a research bot finalizes an answer, before it posts to a room or a task, per claim.

State per claim: { claim, label, receipts, toolManifest }.

Questions:

  • choice, per claim: { measured, inferred, guess } — Given the attached receipts, which label is honest?
  • yes-or-no, per claim labeled guess or inferred: Could a tool in the manifest turn this into a measurement? — pstack's "never hand the human a check you could run", applied to the bot

Code, not questions: receipt present or absent (a measured label with zero receipts is downgraded in code, no judge call), receipt resolvable (the URL or tool id exists in this turn's trace), and the per-answer aggregate.

Bands:

BandConditionAction
acceptjudge label equals bot label at or above thresholdpost; labels render visibly, guesses styled apart from measurements
downgradejudge label is weaker than bot labelrewrite the label to the judge's, post, ledger the disagreement
send-backany claim is guess/inferred and a tool could measure itreturn the claim ids and candidate tools to the bot; one pass only, then post with whatever labels stand
escalatemore than half the claims downgraded, or any confidence in the bottom bandpost with labels and flag the answer for the workspace owner

Fallback on timeout: post with the bot's own labels (today's behaviour plus labels), ledger claim-labeling: unjudged.

Ledger fields: per claim: bot label, judge label, confidence, receipt count, measurable-by-tool answer, candidate tool, whether the send-back produced a receipt.

Blind set (30 minimum, cases are single claims plus receipts):

  • measured with a real receipt that supports it
  • measured with a receipt that does not say what the claim says (must downgrade)
  • an inference dressed as a fact ("the client's traffic dropped" with only a screenshot of one day)
  • a guess with no receipt that a tool could settle ("the site probably uses WordPress" when a fetch tool exists)
  • a guess no tool could settle (a competitor's private pricing)
  • correctly labeled inferred chains (two measured claims plus a stated inference)

Done when: blind set passes, labels render in rooms and reports, downgrade rate per bot is visible in admin, and the completion-check eval still passes with labeled claims as its input.

Policy 4 — Room hygiene

Shared rooms carry conclusions and pointers, never working-out. The Titan.bot Marketing Team room today shows Titan posting multi-paragraph reasoning into a four-member room; every member's next turn then pays for that reasoning as context. pstack solves this with subagent isolation (discovery runs apart, only conclusions promote, file pointers travel, readonly agents lose write-capable tools). Most of it is plumbing in rooms, not judgment.

Rules (enforced in code):

  • A bot's reasoning trace stays in its private trace, viewable by the workspace owner from the bot's page. It is never written to a room message body.
  • A room post is one of: a conclusion, a question (after ask-gate), a status line, or a pointer. Nothing else posts.
  • Pointers, not payloads. A fetched page, a file, a tool result or a ledger entry is linked by id; the content is never inlined into the room. Hard cap on room message length; anything over it must be a pointer to an artifact.
  • Subagent results promote through a structured summary { conclusion, receipts[], openQuestions[] }, never the subagent's raw output.
  • Readonly roles (reviewers, auditors, research-only bots) run with write-capable MCP tools stripped from their manifest at dispatch. The manifest passed to ask-gate and claim-labeling is the stripped one.
  • Room context handed to a bot's next turn is assembled from these posts, so keeping them small is what keeps the 75M-token allowance from draining on rooms.

Optional decision — promotable (build only if rule 2 cannot be settled by message type alone):

  • yes-or-no, per outbound room message: Is this a conclusion or status, rather than working-out?
  • Bands: post above threshold; hold below — the message goes to the bot's trace instead, with a one-line status posted in its place; bottom band posts and flags.
  • Fallback on timeout: post (today's behaviour), ledger promotable: unjudged.
  • Blind set: conclusions, status lines, questions, raw chain-of-thought, a conclusion buried inside three paragraphs of reasoning (must hold), a long but legitimate summary (must post).

Done when: no room message body contains a reasoning trace, room message p95 length drops and stays down, tokens-per-room-turn is charted in admin, and readonly bots cannot be shown a write tool in their manifest.

Decision 5 — playbook-route

A task goes in, a playbook id and a confidence come out, and every step of that playbook must end with a disposition before the task can be called done. pstack does this with a 2,635-word router prompt that picks from 23 markdown playbooks and a rule that skipped steps keep skip: <reason>. Here the pick is a typed choice, the playbooks are data, and "did every step get a disposition" is a loop in code. Routing becomes a ledger row instead of a reasoning paragraph.

Prerequisite — playbooks as data. A playbook is a JSON file, not markdown:

{
  "id": "social-campaign-launch",
  "appliesTo": "one paragraph, written for the judge, on when this playbook is the right one",
  "notFor": "one paragraph on the nearest wrong fits",
  "roles": ["marketer"],
  "steps": [
    { "id": "s1", "text": "...", "verify": "tool | receipt | human | none" },
    { "id": "s2", "text": "...", "verify": "receipt" }
  ]
}

appliesTo and notFor are the only text the judge reads. Start the catalog with the playbooks Titanium Bot already sells (the marketplace copy already calls them playbooks): the marketer flows, the research flows, and the engineering desk flows. Keep it under 255 entries per role so the choice stays single-stage.

Fires: once per task, after task-restatement accepts. Re-fires only if the bot explicitly requests a re-route, and that is its own ledger row.

State: { task, restatement, botRole, workspaceType, catalog: [{ id, appliesTo, notFor }] }, catalog filtered by role in code before the call.

Questions:

  • choice, once: the playbook id from the filtered catalog
  • yes-or-no, once: Does no playbook in this catalog fit? — the honest-abstain question; without it the judge is forced to pick the least-wrong option

Code, not questions: role filtering, catalog size, copying steps into the bot's task list verbatim, and the disposition check.

Disposition check (code, runs at completion): every step id in the chosen playbook must have exactly one of done: <receipt>, skip: <reason>, or blocked: <reason> in the task record. A step with no disposition, or a done with no receipt where verify is receipt, fails the task before completion-check is ever asked. No judge is involved; this is the part that cannot drift.

Bands:

BandConditionAction
routea playbook chosen at or above threshold and no-fit below thresholdcopy its steps into the task, proceed
confirmchosen but in the middle bandproceed, but post a one-line "working from \<playbook>" status the workspace owner can override
no-fitno-fit above thresholdproceed with no playbook (today's behaviour), ledger the task as a catalog gap
escalatebottom band on either questionroute to the approval path with the top two candidates

Fallback on timeout: no playbook (today's behaviour), ledger playbook-route: unjudged.

Ledger fields: chosen id, confidence, no-fit answer, band, override by owner (if any), and at completion the disposition tally: done/skip/blocked counts and every skip reason verbatim. Skip reasons are the review surface; a playbook whose steps are skipped often is a playbook to rewrite.

Blind set (hardest of the five; 30 minimum, more is better): a labeled set of real tasks from the feedback and admin data, each with the correct playbook id or none, including near-miss pairs (a campaign launch vs a campaign report), tasks that fit two playbooks where one is clearly better, tasks outside the catalog entirely, and tasks whose wording mentions a playbook's name but means something else. The case author picks labels without seeing appliesTo text.

Why last: the catalog must exist as data first, and the no-fit rate over the first weeks tells you which playbooks to write next. That feedback loop is worth more than the routing itself.

Done when: blind set passes, disposition check has offline tests for every combination, no task can complete with an undispositioned step, the route and its confidence show on the task in the console, and admin charts no-fit rate per workspace.

Cross-cutting

All four decisions write to the one ledger, share one policy file, and are visible in the same admin panels the feedback and spend views already use.

Ledger. One table, one row per judgment, the schema completion-check uses today plus a decision column and a JSON answers column. No per-decision tables. The unjudged fallback flag is a band value, not a null, so it can be counted.

Policy. One policy.json entry per decision with every band's threshold and action. Thresholds start at the values the blind set eval reports, and change only by editing that file; no threshold lives in code.

Order in the pipeline for a task that touches all of them:

task arrives→task-restatement→playbook-route→bot works
each outbound message→ask-gateclaim-labelingpromotable / room rules
at the end→disposition check→completion-check

A task that fails the disposition check never reaches completion-check.

Restatement and route run once at the start; the three outbound gates run per message; the disposition check and completion-check run once at the end. A task that fails the disposition check never reaches completion-check.

Budget. Per task, the fixed cost is two Jev calls (restatement, route) plus per-part questions; the variable cost is one call per outbound question, per claim, and per room post. At Jev's $0.042 per million input tokens with free output, a task with 20 claims and 5 questions stays under a cent. Latency budget per gate is the completion-check envelope, p50 near 171 ms. The gates that sit in the send path (ask-gate, promotable) must run in that envelope or fall back; nothing in the send path waits past its timeout.

Judge. Jev for all of these today. The code judge for every offline test. The ledger is what makes a fine-tuned local judge on the Nemotron fleet possible later; playbook-route will produce the most training rows soonest.

Admin. Each decision gets one row in the existing admin tables: judgments per day, band distribution, unjudged rate, and the decision's own metric (restatement revise rate, ask-gate false positives, downgrade rate, no-fit rate, tokens per room turn). No new panel; the existing feedback view already has the shape.

Customer-visible. The console footer already shows a judgment and its confidence with a "wrong" button. Every decision here surfaces the same way on the object it judged (the task, the message, the claim) so the wrong button feeds the same feedback table and, later, the blind sets.

Definition of done

A decision is done when all seven hold; the per-decision sections above add the specific metric.

  • ☐policy.json entry with every band, including the bottom, and its action
  • ☐Offline tests against the code judge for every band, the timeout path, and the fallback restoring today's behaviour
  • ☐Blind set of at least 30 cases, authored by someone who did not write the questions and never saw a result, committed to cases/ before the first live eval
  • ☐One live eval run recorded in the repo, no tuning after it; if it fails, the questions change and a new blind set is written
  • ☐Ledger rows land with the shared schema and are queryable in admin
  • ☐The judgment and its confidence are visible on the object it judged, with the existing wrong button wired to it
  • ☐Cost and p50 latency per call measured over the first week and within the completion-check envelope

The promotable decision and the playbook data format follow the same list. The room-hygiene rules are done when the code checks in the Policy 4 section pass.

Deliberately not borrowed

Six pstack mechanisms stay out, each for a stated reason.

pstack mechanismWhy not
The 81k-word instruction stack and 21 principle leavesAssumes a frontier model re-reads it every turn; on Nemotron 30B and GLM-5.3 Flash it degrades and eats the allowance. The ideas above are encoded as data and code instead.
Citation as proof-of-load (may cite only principles read this session)Solves a prompt-loading problem this design does not have; the ledger is the proof here.
20 of the 23 playbooksAbout shipping code. The engineering desk bots are the only fit; put a port with a Claude Code adapter in the e2b sandbox template for them and leave it there.
"Land the stack even if CI flakes"A signal override shipped as a feature. completion-check exists to do the opposite.
Cloud agents over worktreesVendor argument; not relevant to a hosted product with its own fleet.
Cross-family model split (one model for code, another for judgment)Worth revisiting, not now. Jev is already a different family from every generation model in the fleet, which is the point of the split.

Open questions

Answer these before Claude Code starts; each changes a build choice.

  • ☐Who writes the five blind sets? It cannot be whoever writes the questions, and it cannot be Claude Code if Claude Code writes the questions.
  • ☐Does the parts extraction in completion-check run early enough to feed task-restatement, or is it currently built from the claimed result?
  • ☐What is the receipt format today, exactly? claim-labeling and the disposition check both depend on reusing it unchanged.
  • ☐Which sold bots become the first playbook catalog entries, and is there a role field on bots already that the catalog filter can use?
  • ☐Does the approval path exist as a single call site the escalate bands can all target, or is it per feature?
  • ☐Should ask-gate apply to scheduled and nightly bots, where no human is present to receive a passed question anyway?
  • ☐Is the room message body the right place to enforce the length cap, or does the cap belong at the room-context assembly step?
